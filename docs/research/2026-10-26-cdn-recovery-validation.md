# 2.16.0 CDN 救援与零速等待验收

日期：2026-10-26（Asia/Tokyo）。基线：`9123e48` / 2.15.0；候选：本次隔离工作区 2.16.0。未发布、未安装进用户日常 Chrome。实现保存在本次聊天附着的隔离工作区；主目录存在另一组进行中的弹窗/删除改动，本次没有覆盖或合并它们。

## 结论

增加了 hw、ali、alib、hwb 四个兼容 UPOS 镜像候选，保留原清单优先，并修复槽位饥饿、主备同时无进展及语言前缀页面漏注入。受控故障恢复明显改善，健康线路没有可据以认定的加速；全线路故障会多花探测成本。因此不能声称所有场景更快。

用户描述的是“画面卡住，同时 0 KB/s”。本次没有用户当次视频、请求状态和统计快照，不能证明那一次就是以下某个根因；以下区分已复现缺陷、正常零速和仍待现场判断的情况。

## 1. 已复现与修复

1. **救援排队饥饿**：普通槽位都被等待首字节的请求占住时，备用副本也需要同一槽位，只能等原请求超时。新增两条仅供急需备用/对冲的救援槽；普通尝试仍为 32，后台准入仍为 12，每页物理尝试上限 34。
2. **主备同时无进展**：旧版只发一个竞争副本，两者都卡住时不会继续探索。新版保留首个原请求，在备用连续无进展达到两倍对冲阈值且仍有候选时轮换该备用；持续出字节的连接不轮换。
3. **语言前缀漏注入**：真实 B 站把 `/video/BV11En46qETe/` 跳到 `/zh-Hans/video/...`，原 manifest 未匹配，实测页面 `observer=false`。新版真实页面 `observer=true`；浏览器回归还覆盖 zh-Hans、zh-Hant、en 视频页及语言前缀列表页、MAIN/ISOLATED、fetch/XHR 命中和 runtime.reload 后的 bundle SHA-256。
4. **扩展等待有总预算**：每个调度器急需范围的排队、镜像校验与重试共用 12 秒预算，失败交还原生路径；离线镜像查询另有原本最多 1.5 秒的边界。该预算不是“保证 12 秒内恢复播放”。
5. **镜像校验生命周期**：独立审查补出并修复了“首等待者取消误伤其他请求”和“后台校验排队后无法随播放器提升优先级”。新增 red→green 回归；独立校验自己持有槽位、最后等待者离开才取消，优先级取自当前等待者。

## 2. 新候选的使用边界

- 仅从 `upos-sz-mirrorcosov.bilivideo.com` / `upos-hz-mirrorakam.akamaized.net` 的 `/upgcxcode/*.m4s` 生成镜像域名；不改写任意域名、P2P、直播或普通 MP4。
- 四个目标是 `upos-sz-mirrorhw.bilivideo.com`、`upos-sz-mirrorali.bilivideo.com`、`upos-sz-mirroralib.bilivideo.com`、`upos-sz-mirrorhwb.bilivideo.com`，均在已有媒体主机权限内；未增加权限。
- 正常清单路径成功时不主动测速镜像。先取得原清单文件头前 1 KiB（小文件用完整长度），镜像前缀和总长匹配后才下载其他范围；这是内容一致性的快速检查，不能等同完整文件哈希证明。
- 身份未建立的冷启动不会探索镜像。每个实际媒体 Range 继续执行 206 / Content-Range / 正文长度 / 总长校验；错误候选退避，原清单与原生请求仍可回退。
- 本次新增候选仅接入在线播放；完整离线下载器不变。没有在引擎下面叠加全局 DNR 换域名。

## 3. Chromium 受控前后对照

命令：`npm run test:cdn`。加载旧版和新版真实调度器，通过 Chromium 发真实 fetch；网络延迟、HTTP 503、挂起、错误镜像由浏览器路由注入。每类每版 3 次，交错版本次序，下表为中位数。断言媒体字节正确、取消后资源归零、健康场景没有镜像探针；计时从预先取得身份后的请求开始，不包括首次页面打开或解码。

| 场景 | 旧版 2.15.0 | 新版 2.16.0 |

| 主节点等待首字节，备用可用 | 850 ms，成功 | 847 ms，成功 |
| 32 个普通槽全部等待首字节 | 2541 ms，成功 | 918 ms，成功 |

- 饱和槽位场景约缩短 64%。其余健康/高延迟/单节点故障/拖动/双轨的毫秒差异很小，仅 3 次样本，不能宣称普遍提升。
- “主备都挂起”等行的旧版是失败，新版是成功；不能把失败耗时与成功下载耗时相除，当成同口径吞吐提升。
- 健康场景两版接收 262144 字节、4 次请求，未增加镜像流量。全线路立即失败时，两版中位请求数为 16 / 20，额外四次为共享的失败镜像校验。这解释了新版更慢的代价。
- 基线保存在 Git 历史；原始本地明细在开发态 `.tmp/cdn-recovery/comparison.json`。这不是自然 CDN 线路测速，也不是首次出画/所有画质/所有网络的证明。

## 4. 真实 CDN 探测

独立匿名 Chromium 打开真实视频，浏览器内请求相同 64 KiB Range，仅保存主机、状态、长度、SHA-256 和计时，不保存签名 URL 或 Cookie。样本视频为 `BV11En46qETe`，AVC 与 AAC 轨。

| 目标 | 本次观察 |
| --- | --- |
| cosov 原线路 | 视频 26–30 ms / 64 KiB |
| akam 清单备用 | 视频 100–240 ms / 64 KiB |
| hw | 视频 692–950 ms / 64 KiB，字节哈希一致 |
| ali | 视频 610–970 ms / 64 KiB，字节哈希一致 |
| alib | 两轮、音视频均在 6 秒边界超时 |
| hwb | 视频 595–1062 ms / 64 KiB，字节哈希一致 |

这是单个出口、短时间、小样本，可能受到 CDN 热缓存影响，不能外推日本所有网络。它已经足以否定“新增镜像必定比原线路快”，因此没有将这些域名设为强制优先。

## 5. 真实播放器验收

命令：`npm run test:live:playback -- --fail-originals` 与 `npm run test:live:playback -- https://www.bilibili.com/video/BV1rp4y1e745/`。

- `BV11En46qETe`：先正常播放并取得身份，再人为阻断本轮清单主备域，拖到 721.05 秒；镜像仍直连真实 CDN。新版通过 hw 实际取回媒体，最终播放到 740.73 秒，前方播放器缓冲 41.3 秒，扩展前方就绪约 90 秒，原生回退 0。此过程发生一次约 1.46 秒等待（含 seek），并非零等待。
- `BV1rp4y1e745`：不注入线路故障，拖到 190.85 秒后正常推进到 211.53 秒；使用原清单域，未触发新增镜像请求。
- 两次均为独立匿名 profile，不使用用户登录资料。测试后关闭并清理 profile。测试分辨率记录在开发态 JSON；不把匿名 AVC 验证当成 4K、AV1、HEVC 或会员画质验收。
- 截图位于开发态 `.tmp/cdn-recovery/live-fault.png` 与 `live-seek.png`。人为阻断原线路不等于自然复现用户当次卡顿。

## 6. 0 KB/s 的判断

- **画面持续推进、前方就绪约 90 秒、没有在途请求**：可能只是窗口已满，插件暂停预取。本次真实正常播放就多次出现这种零速，无需连续下载来维持一个非零数字。
- **画面不前进、缓冲耗尽、仍有在途/排队请求**：可能在等首字节、正文停滞、救援排队或进入失败退避。本次修复了可复现的队列与候选轮换缺陷。
- **页面加速引擎未注入**：原语言前缀页面已实测存在这个缺陷；此时扩展无从介入播放器网络。
- **所有原线路和镜像都不可用、签名过期或权限拒绝**：更多并发不能制造可用线路，需要看真实 HTTP 状态与当前清单；本次没有证据证明用户当次遇到了哪一种。

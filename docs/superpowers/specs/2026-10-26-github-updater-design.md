# 双渠道更新设计（最终方案 A）

2026-10-26 用户最终选择 A。本文件取代此前官网更新页和商店隔离模块方案。

- 商店版继续提供完整缓存功能；关于页只增加 GitHub 下载链接。累积更新按现有商店审核流程提交。包内不含 GitHub 更新页、文件更新引擎及 GitHub 网络权限。
- GitHub 版以解压目录加载；首次手动安装含更新器的版本，之后在扩展内部检查正式发布、选择实际安装目录、确认写权限、下载校验、替换文件并重载。不安装本机助手，不跳转官网授权目录。
- Chrome 开发者模式须保持开启；扩展内部目录句柄可保存，但重载后写权限可能回到 prompt。每次需要时由用户确认。
- 商店与解压版是独立安装，缓存不会自动迁移。不要求先卸载商店版；避免同时启用两份扩展。

## 信任与发布

GitHub Release 同时附带 `haineicunzhi-github-<version>.zip` 和 `.update.json`。二者来自同一文件快照。后者以 ECDSA P-256 / SHA-256 签名原始 payload 字节，包含渠道、协议、版本、兼容声明、每个文件的内容、长度及 SHA-256。公钥随首次安装包固定，私钥由开发者离线保管；普通更新不轮换公钥。

检查固定仓库最近 20 个发布，跳过草稿、预发布及没有指定更新资产的版本；只接受数字更高版本。可选域名权限在用户主动检查时申请，下载不携带站点凭据。签名、哈希、总大小、路径、清单引用、Chrome 最低版本、权限范围全部通过后才准备写文件。网络元数据自身不作为信任依据。

签名验证针对原包；允许的本地转换只有保留当前 manifest.key（包括原先缺失）和向既有 CDN DNR initiatorDomains 加入当前 ID。转换后的文件单独读回核对。新增权限、变更外部连接或扩展入口要求手动升级。签名不能替代发布前代码审查与数据兼容测试。

## 文件事务与运行协调

目录通过随机 challenge 文件验证：所选目录写随机值，由当前运行扩展的资源 URL 读取同值。拒绝开发仓库根和另一份相同版本目录，避免更新错误副本。

后台锁和暂停清单存 storage.local；另存为在途标记放 storage.session。更新前拒绝仍在保存的任务，先持久化锁及下载清单，再关闭 offscreen 操作闸门，等待已进入的命令、下载写入和合并结束。新缓存／保存／播放合并在锁内拒绝。

多个更新页通过 Web Lock 对文件写入、恢复、取消及健康提交互斥；重载销毁旧上下文才释放写入锁，15 秒未重载则超时转恢复。独立 IndexedDB `haineicunzhi-updater-v1` 保存目录句柄和原文件快照，原片库数据库名不变。所有目标文件的旧字节必须先持久化，才逐个写入并按哈希读回；manifest 最后写。失败恢复旧字节并删除本次新建文件。恢复未完成保留日志和锁。v1 不删除旧版本的额外文件，也不触碰缓存。

重载前写持久状态；新后台打开续接页，确认 manifest 目标版本和新 offscreen 版本后才清理快照、解锁并尝试续传。默认刷新 B 站视频／列表页，用户可取消勾选；刷新让内容脚本用上新版本。续传失败单独提示。

关闭更新页或浏览器后可重新进入恢复；恢复需要目录写权限。若新扩展连更新页也无法运行，手动以可信 ZIP 覆盖原安装目录并重载。多文件写入不具备全局原子性，不宣称任意崩溃都能自动回滚。

自动更新只用于向后兼容的数据变更；新版本通过健康检查前不得执行不可逆迁移。不兼容升级必须单独发布手动流程。

# 播放位置感知的内存回收

> 对应能力：播放缓存第 4 项「播放感知回收」。临时容量边界仍是 128 MiB。
> 本文只描述回收策略；缓存命中、请求适配和预热调度见
> [播放缓存设计](playback-cache-design.md)。

## 1. 为什么替换简单 FIFO

原 `playback-cache.js` 的回收完全按块的插入顺序：谁先写进来，谁先被回收。它有三个问题：

1. **保护不了正在播放的数据。** 刚预热的头部初始化区或当前窗口，可能因为插入时间不算最早，却
   被后来的大块挤出；真正该丢的、离播放位置很远的旧段反而留着。
2. **分不清活跃轨道。** 切清晰度后旧 CDN 地址的整条数据仍和当前轨道同级竞争，等于让旧轨拖慢新轨。
3. **播放位置变化无感知。** 用户拖动后，前方窗口整体平移，FIFO 完全不知道新窗口在哪。

本次引入**保留提示（retention hint）**：由观察器把「用户正在看哪条轨、哪个时间点、前后窗口多大」
告诉缓存，缓存按提示给块分级，再决定回收顺序。策略只改变**回收顺序**，不放松 128 MiB 硬上限。

## 2. 分级与回收顺序

每个驻留块在回收时被归入一个层级（数字越小越先被回收）：

| 层级 | 含义 | 说明 |
| --- | --- | --- |
| 0 | 非活动资源 | 没有保留提示，或提示 `active: false`；优先整条清理 |
| 1 | 活动轨但远离窗口 | 属于当前轨道，但不在初始化/索引区，也不在窗口内 |
| 2 | 保护中的初始化/索引区与窗口 | 活动轨道的头部 + `[position - rewind, position + ahead]` 覆盖的字节区间 |

同级内部：

1. 距最近保护区的字节距离**从远到近**；
2. 距离相同时按块插入顺序（`order` 升序）。

三层键 `(tier, -distance, order)` 全部来自缓存内部状态，结果**确定可复现**，
不依赖时间戳、随机数或 Map 遍历的稳定性。

**保护不阻止回收。** 当整池都落在保护区、而总字节仍超过上限时，层级 2 之间继续按「先远后近、
再按插入顺序」回收，循环直到 `stats.bytes <= limit`。这是硬边界，不允许为保留热数据而突破。

资源条目数上限（32）也做了同样的偏好：优先丢弃非活动条目；全部活动时退回最早插入的条目。
条目被整体丢弃（`discard`）时同步删除它的保留提示，避免清空后仍占保护名额。

## 3. 时间/字节如何对应

### 3.1 有 SIDX：用真实分段

缓存已经解析 ISO BMFF 的 SIDX（见播放缓存设计第 6 节）。回收时把窗口
`[position - rewind, position + ahead]` 与各段的 `[timeStart, timeEnd)` 求交，
命中的段转成字节区间 `[start, end)`。

- 初始化/索引区固定为 `[0, 首段起点)`。
- 窗口与段是否相交只看时间，不按码率估算时间。
- 窗口跨越段边界时取并集，避免只保护半段。

### 3.2 无 SIDX：按比例回退

索引不可用时退回按总大小/时长比例估算：

```text
perSecond = total / duration
保护字节窗口 = [ floor((position - rewind) * perSecond),
                 min(total, ceil((position + ahead) * perSecond)) ]
```

初始化/索引区退化为 `[0, min(total, 1 MiB))`：1 MiB 是索引探测上限，覆盖 SIDX 可能出现的头部。
这样即使索引尚未解析，活动轨道的头部也不会被先回收。**回退只用于回收顺序，不用于绘制黄色或
声明命中**；时间映射的准确性仍以 SIDX 为准。

## 4. 观察器如何刷新提示

`playback-observer.js` 的 `updateRetentionHints()`：

1. 找到正在播放（或第一个）`<video>`，读取 `currentTime` 与 `duration`；
2. 前方窗口用配置项 `leadSeconds`（默认 45s）；
3. 回看窗口固定为 `RETENTION_REWIND_SECONDS = 5s`，既能覆盖拖动后的小幅回退，又不会保护过多历史；
4. 对每条轨道：`active === false` 调用 `release(url)`，否则调用
   `retain(url, { active: true, position, ahead, rewind, duration, protectInit: true })`。

调用时机有两处：

- `renderPreheatProgress()` 开头：绘制、命中、预热写入都会触发它；
- 400ms 调度周期开头：即使标签页隐藏（rAF 暂停）也会持续刷新位置。

生命周期边界：

- 切换视频/分 P、关闭辅助 → `playbackCache.clear()`，缓存同时清空资源与保留提示；
- 切换清晰度/CDN → 旧轨道被标记失活，提示通过 `release` 删除；
- 轨道 5 分钟未活动被清理时，先 `release` 再删除，防止提示泄漏。

## 5. API

`window.__biliBufferCache` 新增：

| 方法 | 用途 |
| --- | --- |
| `retain(url, hint)` | 刷新某 URL 的保留提示；`hint = { active, position, ahead, rewind, duration, protectInit }` |
| `release(url)` | 删除单条提示（轨道失活/取消） |
| `clearRetention()` | 清空全部提示（导航/关闭） |

`clear()` 会同时清空提示；提示按 URL 隔离，最多保留 64 条，超出时淘汰最早写入的提示。

## 7. 边界与后续

- 提示只影响**回收顺序**；不改变命中语义、请求回退、预热调度或网络策略。
- 无 SIDX 且 `duration` 未知时不做字节回退（无法估算窗口），只保护头部。
- 保护窗口内数据仍可能在整池都受保护时被回收；128 MiB 硬上限优先级最高。
- 关闭辅助后提示被清空，重新开启会按新的播放位置重新建立，不沿用旧窗口。
- 更细的「帧级关键帧/音视频配对」保护不在本次范围。

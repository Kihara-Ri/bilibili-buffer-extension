# 真实 Chrome 并发验证与架构选择

## 结论（2026-09-21，2.8.0 工作区）

保留「预热缓存 → 按需并行救援 → 原生回退」及独立离线片库，不增加 CPU Worker，也不把并发扩到 64/128。

采用 **64 KiB 子块 + 按请求大小分配普通工作者 + 全局最多 32 路**。急需范围每 256 KiB 分配一个工作者：2 MiB 对应 8 路，8 MiB 对应 32 路；用户较低上限优先。救援副本仍占共享全局预算，因此救援时实际连接可以高于单请求普通工作者数。后台预热保持 256 KiB 分块及半数连接限额。离线视频 4 路、音频 1 路不变。

新配置默认 `cdnMode: original`，使用播放清单自己的主备节点。大陆/自动模式仍可选；已有配置的模式和上限不覆盖。`maxConcurrency: 32` 是**上限**，不代表每个请求必须开启 32 路。

这是本次两个视频、当前网络条件下的折中选择，不是所有地区/CDN/4K 视频的普适最优。

## 与用户提供对话的架构对照

已在用户日常登录的 Chrome 中读到指定对话。对话比较的是旧版 **2.6.2**，不是当前工作区：

| 对话建议 | 当前代码路径 |
| --- | --- |
| 预热命中直接给播放器 | `playback-cache.js` 的 fetch/XHR 适配器与内存 Range 缓存 |
| 缓存 miss 后拆分当前请求救援 | `playback-observer.js: loadPlayerRange` → `playback-network.js: download` |
| 多 CDN 竞争，胜出取消副本 | `piece/attempt`，停滞 700 ms 救援，受共享预算限制 |
| 失败完全交还 B 站 | 缓存适配器捕获失败，回退原生 fetch/XHR |
| 在线与离线并发分开 | MAIN world 内存链路；另有 SW → offscreen → IndexedDB → remux |

因此当前架构已实现对话中最有价值的组合，而不是它描述的“miss 后只能单连接”。对本项目兼顾在线播放与离线片库的目标，这种组合更合适；单独追求实时加速的专用插件可以更小、更简单。本次没有重新审计 Thread Ripper 最新代码，对它的描述限于该对话。

“线程”在这里指异步 Range 请求工作者，不是 OS 线程或 `new Worker()`。浏览器网络栈可并发处理 I/O；增加 JS Worker 不会凭空增加带宽。

## 实验方法与验收账本

- 用户要求之后未再启动独立/dev 浏览器。使用 macOS Apple Events 按**已有 Chrome 主进程 PID + 标签 ID**连接，Chrome 153.0.8010.53。
- 在真实 B 站页面内取得播放清单，沿用该页面登录会话；cookie、token、签名媒体 URL 不写入仓库或日志。JSON 仅保留 BV 号、编码、主机和测量数据。
- 两个视频：`BV1KNPHzPEra`（1080P AVC）与 `BV1jU4y1A7w4`（1080P HEVC）。不是 4K 压力测试；未独立鉴定 VPN/代理路径。
- 原样运行生产下载器；固定档位实验仅在临时工厂中替换块大小/请求预算/硬上限，不更改生产配置。`current-policy` 不替换源代码。
- 用同源空 iframe 的原生 fetch 绕过页面插件缓存，`cache: no-store`。每组读取相同完整范围，逐次验证 206、Content-Range、长度及 SHA256；CDN 边缘缓存仍可能变热。
- 每组 3 轮，轮换/反转顺序。第二视频交错测试 original/auto/mainland，降低不同时段比较的偏差。3 个样本只能给出描述性的中位数和最大值，不能称作可靠 P95/P99。
- 记录完整片段耗时、请求数、实际并发峰值、HTTP 错误、应用读取字节。应用字节包含已读竞争副本，但不包含协议头、传输层重传、取消后浏览器底层仍收到的字节，因此不是抓包总流量。

| 验收项 | 结果 |
| --- | --- |
| 读取对话并追踪当前执行链路 | 完成 |
| 真实浏览器 1/4/8/16/32 与 64/128 对照 | 完成，120 次样本均完成且 SHA256 一致（各自媒体范围内） |
| 小片段、大范围与第二视频交叉验证 | 完成，见下表 |
| 先失败测试再改策略 | 新增策略测试先出现 3 项预期失败，修改后通过 |
| 默认值、手动配置保留、低上限、8 MiB 上限 | 单元测试覆盖 |
| 真实 fetch/XHR 完整链路 | 冷 fetch、按需加速、暖缓存、XHR 命中、强制下载失败后的原生回退、AbortSignal 均通过 |
| 工程校验 | `npm test` 145 项通过；`npm run check`、`npm run build` 通过 |

端到端链路是在真实视频页临时注入当前源码验证，禁用探针的周期预热以隔离行为，结束后刷新页面清除注入。**不等同于已在用户 profile 安装/重载新扩展包**。本次没有为运行 Playwright 集成套件另开浏览器，也不把早先本地受控网络实验当作实网证据。

## 实测结果

单位：毫秒，越低越好。下表按同组比较，不把前后时段的绝对耗时直接当作 CDN 因果结论。

### 视频一，2 MiB，原清单节点，64 KiB 分块

| 方案 | 中位数 | 最大值 |
| --- | ---: | ---: |
| 原生单请求（不拆分） | 1300 | 2017 |
| 1 路 | 1396 | 1756 |
| 4 路 | **398** | 1181 |
| 8 路 | 432 | **619** |
| 16 路 | 485 | 796 |
| 32 路 | 863 | 894 |

4 路的中位数略好，但 8 路这组的最大耗时明显较低；选择 8 路作为 2 MiB 的普通工作者预算。不能把三次采样的最大值解释为稳定尾延迟保证。256 KiB / 8 路为 795 ms，中位数不如 64 KiB / 8 路。

### 视频一，8 MiB，原清单节点，64 KiB 分块

| 上限 | 中位数 | 最大值 | 三轮总请求数 | 三轮应用读取量 |
| --- | ---: | ---: | ---: | ---: |
| 8 | 2031 | 2315 | 388 | 25,165,824 B |
| 16 | 1846 | 2094 | 412 | 25,182,022 B |
| **32** | **1356** | **1658** | **418** | **25,165,824 B** |
| 64 | 2007 | 2079 | 511 | 25,358,440 B |
| 128 | 2081 | 2239 | 511 | 25,620,227 B |

实际峰值确实达到 64/128，不是只修改显示上限。比 32 路增加一倍/三倍并发，反而更慢，且救援请求更多。保留大范围可用 32 路，但不扩大生产硬上限。

### 视频二，2 MiB，交错测试线路与块大小

| 方案 | 原清单中位数 | 自动中位数 | 大陆优先中位数 |
| --- | ---: | ---: | ---: |
| **64 KiB / 8 路** | **825** | 1067 | 2618 |
| 64 KiB / 32 路 | 883 | 2994 | 3053 |
| 256 KiB / 8 路 | 1511 | 1616 | 1959 |

该组原生单请求中位数 1485 ms，最大值 16895 ms。原清单内已有可用海外节点；强行合成大陆地址没有显示收益。默认选择原清单主备，不删除其他模式。

### 实际修改后的源码复测（视频二，2 MiB）

| 方案 | 中位数 | 最大值 | 实际峰值 |
| --- | ---: | ---: | ---: |
| **current-policy（原样生产代码）** | **870** | 1768 | 8 |
| 固定 8 路 | 1126 | 1302 | 8 |
| 固定 32 路 | 1243 | 1255 | 32 |

新策略中位数较固定 32 路低约 30%，但最大值没有更优；不宣称所有时刻都更快。最终取舍是避免无收益的大量连接，同时保留大请求和故障救援能力。

## 复现

只适用于 macOS，需 Node 和已打开的 Chrome。用户先开启「查看 → 开发者 → 允许 Apple 事件中的 JavaScript」，打开受测 B 站视频，并提供 Chrome 主进程 PID 与标签 ID。脚本会激活目标标签、临时暂停视频，完成后恢复播放状态；实验期间不要切换/关闭目标页。

```sh
# 默认 2 MiB，三轮；含原样策略和固定并发/分块矩阵
npm run bench:real -- <PID> <TAB_ID>

# 大范围，真正覆盖 64/128 路；约 144 MiB 有效正文，另有探测/救援流量
BENCH_MIB=8 npm run bench:real -- <PID> <TAB_ID>

# 定向交错对照线路，减少不必要流量
BENCH_CDN=compare BENCH_CASES=native-single,64k-8,64k-32,256k-8 \
  npm run bench:real -- <PID> <TAB_ID>

# 原样生产代码和两档固定并发的复核，避免覆盖先前结果
BENCH_LABEL=selected BENCH_CASES=current-policy,64k-8,64k-32 \
  npm run bench:real -- <PID> <TAB_ID>
```

`BENCH_ROUNDS` 可设 1–5。结果位于 `.tmp/real-concurrency/`，文件含时间、源码 SHA256、逐次记录和汇总；该目录已忽略，不提交原始实验日志。本次主结果文件：

- `BV1KNPHzPEra-2MiB-original.json`
- `BV1KNPHzPEra-8MiB-original.json`
- `BV1KNPHzPEra-2MiB-mainland.json`
- `BV1jU4y1A7w4-2MiB-compare.json`
- `BV1jU4y1A7w4-2MiB-original-selected.json`

失败样本保留，不能只删除失败结果后报告速度。单次样本有下载截止时间；取消页内实验可调用 `window.__biliRealBench?.cancel()`。测试完成后可关闭 Apple Events JavaScript 权限。
